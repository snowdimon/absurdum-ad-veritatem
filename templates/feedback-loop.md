# Механизм обратной связи

> **Назначение:** замкнуть петлю обучения системы на основе инцидентов абсурда.
> Обеспечить, чтобы каждый инцидент приводил к конкретным изменениям в архитектуре,
> Карте сценариев, метриках или процессах — и чтобы эти изменения отслеживались.

---

## Принцип работы

Каждый инцидент, зафиксированный в Журнале, запускает цепочку:

Инцидент → Анализ → Обновление Карты → Пересчёт метрик → Корректирующие действия → Верификация


---

## Этапы механизма

### 1. Фиксация инцидента

- Инцидент заносится в Журнал инцидентов абсурда (`incidents/`).
- Присваивается уникальный ID.
- Если сценарий новый (отсутствует в Карте) — немедленно создаётся черновик записи в Карте.

### 2. Классификация и анализ

Каждый инцидент классифицируется по типу:

| Тип инцидента | Описание | Пример |
| :--- | :--- | :--- |
| **Коллапс** | Система разрушилась или стала нефункциональной | Отказ в доступе к шлюзу |
| **Деградация** | Система сохранила функцию, но потеряла ключевые свойства (честность, узнаваемость) | Стек опыта стал инструментом неравенства |
| **Неожиданное поведение** | Система не коллапсировала, но повела себя непредусмотренным образом | Неверная интерпретация статуса риска |
| **Новый сценарий** | Сработал гротескный предел, которого не было в Карте | Комбинированная атака на два правила одновременно |

### 3. Обновление Карты абсурдных сценариев

- Если инцидент относится к существующему сценарию: уточняются индикаторы приближения, вероятность, ущерб.
- Если инцидент новый: создаётся запись в Карте (`AS-XXX`).
- Если инцидент показывает, что контрмера неэффективна: статус сценария меняется на «Открыт», требуется новая контрмера.

### 4. Пересчёт метрик

Метрики пересчитываются немедленно:

- **DRC** — уменьшается, если сценарий перестал проходиться.
- **GLM** — уменьшается, если новый сценарий снизил порог коллапса.
- **FPI** — уменьшается, если инцидент вызван абсурдным запросом, который система не обработала.
- **ICI** — уменьшается, если инцидент вскрыл новое противоречие.

Новые значения фиксируются в истории метрик.

### 5. Корректирующие действия

На основе анализа инцидента назначаются действия:

| Серьёзность | Действие | Срок |
| :--- | :--- | :--- |
| Критический | Остановка релиза, экстренное исправление, повторный стресс-тест | Немедленно |
| Высокий | Назначение доработки, включение в следующий цикл тестирования | До следующего релиза |
| Средний | Добавление в бэклог, обновление документации | Планово |
| Низкий | Фиксация, мониторинг, пересмотр на ретроспективе | По необходимости |

### 6. Верификация исправлений

- После внесения изменений проводится повторное гротескное прототипирование по сценарию, вызвавшему инцидент.
- Результаты фиксируются в Протоколе стресс-тестирования.
- Если сценарий пройден: статус в Карте меняется на «Проработан» или «Закрыт», метрики пересчитываются в сторону улучшения.
- Если не пройден: цикл повторяется.

## Ретроспектива инцидентов (ежеквартально)

Раз в квартал проводится сводный анализ всех инцидентов за период:

- Какие сценарии срабатывали чаще всего?
- Какие домены системы наиболее уязвимы?
- Какие метрики показывают отрицательный тренд?
- Какие контрмеры доказали эффективность, а какие требуют замены?

Результат ретроспективы — **отчёт об абсурд-устойчивости системы**, который включает:

1. Текущие значения всех метрик и их тренд.
2. Список топ-5 критических сценариев.
3. План доработок на следующий квартал.
4. Обновлённая Карта абсурдных сценариев (vN).

## Пример из Duranki

**Инцидент:** INC-001 (блокировка шлюза при потере связи).

**Цепочка:**
1. Инцидент зафиксирован в Журнале (`INC-001`).
2. Классифицирован как «Коллапс» по сценарию `AS-002`.
3. Сценарий `AS-002` переведён в статус «Открыт», уточнены индикаторы.
4. Метрики: DRC снижен до 0.80, GLM остался 2.
5. Назначено корректирующее действие: внедрение кэширования, градация доверия. Срок — до следующего стресс-теста.
6. После доработки проведён тест `ST-002`:
   - Сценарий пройден.
   - Статус `AS-002` → «Проработан».
   - DRC → 0.95, GLM → 3.
7. Инцидент закрыт.

## Ответственные роли

| Роль | Обязанность |
| :--- | :--- |
| Абсурд-инженер | Координация всего механизма, анализ инцидентов, обновление Карты |
| Архитектор | Принятие решений об изменении архитектуры на основе инцидентов |
| Тестировщик | Проведение повторного стресс-теста после исправлений |
| Технический писатель | Обновление документации по результатам |
