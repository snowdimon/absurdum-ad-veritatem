# Руководство по применению принципа превентивной эскалации абсурда

> **Связь с Манифестом:** данный документ — практическое дополнение к
> [Манифесту абсурд-инженера](https://github.com/snowdimon/absurdum-ad-veritatem).
> Манифест отвечает на вопросы «Что это?» и «Зачем?».
> Руководство отвечает на вопрос «Как именно применять?».

---

## 1. Введение

### 1.1 Цель руководства

Предоставить системному архитектору, инженеру или руководителю проекта
конкретные, воспроизводимые процедуры для проверки любой системы
на структурную честность с помощью «Теста Кафки» — процедуры
доведения ключевых правил до гротескного предела.

### 1.2 Термины и определения

| Термин | Определение |
| :--- | :--- |
| **Принцип превентивной эскалации абсурда** | Максима: любая система, правило или идея должны быть спроектированы так, чтобы их предельное, гротескное воплощение не разрушало замысел, а раскрывало его глубинную правду |
| **Тест Кафки** | Процедура доведения правила/системы до гротескного предела с целью проверки на структурную честность |
| **Абсурд-инженер** | Архитектор, который намеренно включает такую проверку в цикл проектирования |
| **Гротескный предел** | Состояние, в котором правило исполняется с абсолютной, карикатурной буквальностью |
| **Структурная честность** | Свойство системы выдерживать собственную карикатуру и узнавать в ней свой исходный замысел |

## 2. Инструменты

Для применения принципа разработан набор инструментов, оформленных как
отдельные шаблоны. Ссылки ведут на соответствующие файлы в репозитории.

### 2.1 Карта абсурдных сценариев

**Назначение:** выявление и документирование потенциально опасных гротескных
пределов ключевых правил системы.

**Шаблон:** [`templates/absurd-scenario-map.md`](templates/absurd-scenario-map.md)

**Порядок работы:**
1. Выявите все ключевые правила системы.
2. Для каждого правила сформулируйте минимум один гротескный сценарий.
3. Заполните таблицу: ID, правило, домен, сценарий, вероятность, ущерб, индикаторы, контрмера, статус.
4. На этапе проектирования создаётся версия v1. Далее Карта уточняется по результатам тестов и инцидентов.

### 2.2 Гротескное прототипирование

**Назначение:** намеренное создание карикатурной, искажённой версии системы
для проверки её поведения в предельных состояниях.

**Чек-лист подготовки:** [`templates/grotesque-prototyping-checklist.md`](templates/grotesque-prototyping-checklist.md)

**Порядок работы:**
1. Подготовьте сценарии — выберите из Карты для текущего сеанса.
2. Сформируйте команду: ведущий, «адвокат дьявола», наблюдатели.
3. Изолируйте среду — тестовая среда не должна влиять на продуктив.
4. Определите критерии остановки и признак успешного прохождения.
5. Проведите сеанс, фиксируя всё в Протоколе стресс-тестирования.
6. Проведите пост-анализ сразу после сеанса.

### 2.3 Протокол стресс-тестирования

**Назначение:** документирование каждого сеанса гротескного прототипирования.

**Шаблон:** [`templates/stress-test-protocol.md`](templates/stress-test-protocol.md)

**Порядок работы:**
1. Заполните поля до начала сеанса: ID, дата, объект, сценарий, метод эскалации, ожидаемый результат.
2. В ходе сеанса фиксируйте фактический результат и обнаруженные инциденты.
3. После сеанса зафиксируйте решение: `Пройден`, `Отклонён`, `Условно пройден`.
4. Пересчитайте метрики, на которые повлиял тест.

## 3. Метрики устойчивости к абсурду

**Назначение:** количественная оценка способности системы выдерживать
гротескные пределы собственных правил.

**Полный файл с формулами и шкалами:** [`metrics/absurd-resilience-metrics.md`](metrics/absurd-resilience-metrics.md)

### Краткий справочник

| Метрика | Обозначение | Что измеряет | Формула |
| :--- | :--- | :--- | :--- |
| Индекс внутренней согласованности | ICI | Отсутствие противоречивых правил | `1 - (P_contra / P_total)` |
| Коэффициент устойчивости к искажениям | DRC | Способность выполнять функцию при гротескной интерпретации | `S_pass / S_total` |
| Метрика гротескной нагрузки | GLM | Количество одновременно активных сценариев до коллапса | `N_collapse` |
| Показатель дуракоустойчивости | FPI | Готовность к абсурдным запросам | `Q_handled / Q_absurd` |

**Периодичность замера:**
- Базовый замер — на этапе проектирования.
- После каждого стресс-теста — пересчёт затронутых метрик.
- В эксплуатации — ежемесячный мониторинг.
- После каждого инцидента — немедленный пересчёт.

## 4. Система документации

### 4.1 Журнал инцидентов абсурда

**Назначение:** документирование всех случаев, когда система столкнулась
с реальным или близким к реальности проявлением гротескного сценария.

**Шаблон:** [`templates/incident-log.md`](templates/incident-log.md)

**Каждый инцидент содержит:**
- Уникальный ID, дату, статус.
- Ссылку на сценарий из Карты (или пометку «Новый»).
- Описание, последствия, метрики до и после.
- Предпринятые действия и извлечённые уроки.

### 4.2 Механизм обратной связи

**Назначение:** замкнуть петлю обучения: инцидент → анализ → обновление Карты → пересчёт метрик → исправление → верификация.

**Полный файл:** [`templates/feedback-loop.md`](templates/feedback-loop.md)

**Цепочка:**

Инцидент → Анализ → Обновление Карты → Пересчёт метрик → Корректирующие действия → Верификация


**Ретроспектива инцидентов** проводится ежеквартально. Результат — отчёт об абсурд-устойчивости системы: текущие метрики, топ-5 критических сценариев, план доработок.

## 5. Интеграция в жизненный цикл системы

**Матрица применения:** [`templates/tool-application-matrix.md`](templates/tool-application-matrix.md)

### Краткая дорожная карта

| Этап | Что делаем | Gate |
| :--- | :--- | :--- |
| **Проектирование** | Заполняем Карту сценариев (v1), проводим базовый замер метрик | ICI ≥ 0.8, иначе ревизия правил |
| **Прототипирование** | Проводим гротескное прототипирование по каждому сценарию, фиксируем Протоколы, обновляем метрики | DRC ≥ 0.8, все критические инциденты закрыты |
| **Тестирование** | Повторный прогон критических сценариев, контрольный замер метрик | DRC ≥ 0.9, FPI ≥ 0.95 |
| **Эксплуатация** | Мониторинг метрик (ежемесячно), фиксация инцидентов, ретроспектива (ежеквартально) | При падении DRC < 0.8 — внеочередной цикл тестирования |

### Ритуалы

- **Gate на этапе проектирования:** ни одно архитектурное решение не принимается, пока Карта не заполнена.
- **Ревью архитектуры:** в чек-лист ревьюера добавлен пункт «Проведена ли эскалация абсурда для критических правил?».
- **CI/CD:** при наличии автоматизации — прогон набора гротескных сценариев в пайплайне (chaotic testing).
- **Ретроспектива инцидентов:** при разборе любого инцидента обязателен вопрос «Был ли этот сценарий в нашей Карте? Если нет — почему?».

## 6. Примеры (кейсы из Duranki)

Duranki — проект межпланетной системы идентификации, в ходе работы над которым
был сформулирован принцип превентивной эскалации абсурда.

### Кейс 1: Буквоед на Марсе

**Сценарий (AS-002):** потеря связи с Earth-Linked Ledger на 14 суток.
**Гротескный предел:** система отказывает в доступе к шлюзу, потому что не может верифицировать данные.
**Результат теста (ST-001):** Отклонён. DRC = 0.80.
**Контрмера:** кэширование данных с TTL 14 суток, градация доверия.
**После доработки (ST-002):** Пройден. DRC = 0.95.

### Кейс 2: Стек как каста

**Сценарий (AS-001):** EVA даёт «статус риска» → страховые коэффициенты привязаны к стеку.
**Гротескный предел:** капитаны гоняют экипаж в открытый космос для «набивки стека».
**Статус:** Проработан. Контрмера: архитектурное разделение «сырого опыта» и «юридических привилегий».
