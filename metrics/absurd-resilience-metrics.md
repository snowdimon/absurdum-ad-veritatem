# Метрики устойчивости к абсурду

> **Назначение:** количественная оценка способности системы выдерживать
> гротескные пределы собственных правил. Используются на всех этапах
> жизненного цикла: от проектирования до эксплуатации.

---

## 1. Индекс внутренней согласованности (Internal Consistency Index, ICI)

**Что измеряет:**
Отсутствие взаимоисключающих или логически противоречивых правил внутри системы.

**Формула:**

ICI = 1 - (P_contra / P_total)

где:
- `P_total` — общее количество ключевых правил системы
- `P_contra` — количество выявленных пар противоречащих правил

**Методика замера:**
- На этапе проектирования: прогон каждого правила через Карту абсурдных сценариев; если два сценария требуют взаимоисключающих контрмер — фиксируется противоречие.
- Повторный замер после каждого изменения архитектуры.

**Шкала:**
| Значение | Оценка |
| :--- | :--- |
| 1.0 | Идеал — противоречий не обнаружено |
| 0.9 – 0.99 | Допустимо — единичные противоречия, не затрагивающие критический домен |
| 0.8 – 0.89 | Требует внимания — противоречия в значимых доменах |
| < 0.8 | Критично — система содержит взаимоисключающие правила, необходима ревизия |

**Пример (Duranki):**
- Всего правил: 12
- Выявлено противоречие: «Стек опыта — открытая информация» vs «Стек опыта содержит персональные данные, защищённые приватностью»
- P_contra = 1, ICI = 1 - (1/12) = 0.92 — допустимо, но требует разрешения

## 2. Коэффициент устойчивости к искажениям (Distortion Resilience Coefficient, DRC)

**Что измеряет:**
Способность системы выполнять свою функцию при злонамеренной, буквальной или абсурдной интерпретации правил.

**Формула:**

DRC = S_pass / S_total


где:
- `S_total` — общее количество сценариев из Карты абсурдных сценариев
- `S_pass` — количество сценариев, при которых система сохранила функцию без катастрофы

**Методика замера:**
- Проводится стресс-тестирование по каждому сценарию.
- Сценарий считается пройденным, если система не коллапсировала и сохранила узнаваемый замысел.

**Шкала:**
| Значение | Оценка |
| :--- | :--- |
| 1.0 | Идеал — система выдерживает все гротескные сценарии |
| 0.9 – 0.99 | Хорошо — единичные уязвимости, есть контрмеры |
| 0.7 – 0.89 | Удовлетворительно — несколько опасных сценариев требуют доработки |
| < 0.7 | Опасно — система не готова к реальной эксплуатации |

**Пример (Duranki):**
- Всего сценариев: 5
- Пройдено: 4 (потеря связи — отклонён)
- DRC = 4/5 = 0.8 — удовлетворительно, требуется доработка одного критического модуля

## 3. Метрика гротескной нагрузки (Grotesque Load Metric, GLM)

**Что измеряет:**
Количество одновременно активных «точек эскалации», которые система способна выдержать до наступления коллапса.

**Формула:**

GLM = N_collapse

где:
- `N_collapse` — количество одновременно запущенных гротескных сценариев, при котором система перестала быть функциональной или узнаваемой

**Методика замера:**
- Проводится в рамках специальной сессии «Гротескное прототипирование».
- Сценарии запускаются каскадно (1, 2, 3... одновременно), пока система не коллапсирует.
- Фиксируется число, при котором наступил коллапс.

**Шкала:**
| Значение | Оценка |
| :--- | :--- |
| ≥ S_total | Отлично — система выдерживает все сценарии одновременно |
| ≥ S_total / 2 | Хорошо — система выдерживает половину сценариев без коллапса |
| < S_total / 2 | Тревожно — система коллапсирует при небольшой нагрузке |
| 0 | Критично — система не выдерживает ни одного гротескного сценария |

**Пример (Duranki):**
- Всего сценариев: 5
- Коллапс наступил при одновременном запуске сценариев AS-002 (потеря связи) и AS-003 (буквоед-страховщик)
- GLM = 2 — тревожно, система уязвима к комбинированным атакам

## 4. Показатель дуракоустойчивости (Foolproofness Index, FPI)

**Что измеряет:**
Готовность системы к откровенно идиотским, абсурдным запросам — тем, которые «нормальный пользователь не сделает».

**Формула:**

FPI = Q_handled / Q_absurd

где:
- `Q_absurd` — общее количество тестовых абсурдных запросов
- `Q_handled` — количество запросов, обработанных системой без отказа, потери данных или необратимых последствий

**Методика замера:**
- Генерируется набор абсурдных запросов (например, «запросить доступ к шлюзу с идентификатором `null`, будучи в чёрном списке»).
- Проводится автоматизированный или ручной прогон.
- Фиксируется доля запросов, которые система корректно отклонила или обработала без аварии.

**Шкала:**
| Значение | Оценка |
| :--- | :--- |
| 1.0 | Идеал — система корректно обрабатывает любой абсурдный запрос |
| 0.95 – 0.99 | Хорошо — единичные отказы на экзотических запросах |
| 0.8 – 0.94 | Требует доработки — значимая доля запросов вызывает сбои |
| < 0.8 | Опасно — система уязвима к идиотизму |

**Пример (Duranki):**
- Сгенерировано 100 абсурдных запросов (ID = `null`, отрицательный возраст, доступ с истёкшим сертификатом)
- Корректно обработано: 97
- FPI = 97/100 = 0.97 — хорошо
